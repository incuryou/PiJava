# 架构与后续路线

## 当前实现

Switch 宿主以主线程配合两个工作线程协作。工作池的 `threadCreate(..., i+1)` 把工作线程置于 CPU 1、2；NSP 已锁定 NPDM 的默认 CPU 是 0，允许范围为 0—2。NRO 主线程由 hbloader 环境安排。音频使用第一个工作线程，GC 跟踪可使用两工作线程，部分原画 CPU 像素准备可拆分；异步日志线程复用 CPU 2。

因此项目已实现三个 CPU 核心参与的任务分工，但不等于三个 Java 执行器并行执行，也不意味着三个核心持续满载。Java 侧线程仍在宿主执行器中协作调度。相关入口为 `src/p7_worker.h`、`src/async_log.inc` 与 `src/j2mevm.cpp`。

GPU 通过 `src/switch_gpu_present.h`、`shaders/filter.vert` 和 `shaders/filter.frag` 完成五种显示滤镜与呈现。关闭滤镜用 CPU；菜单/遮罩等仍包含 CPU 合成。显示槽、fence、缓存键与失败回退用于管理 CPU/GPU 生命周期。这不是完整 3D 硬件渲染支持。

## 后续计划

1. **完善 3D 支持**：扩展 M3G 与 Mascot Capsule 的兼容覆盖、几何/纹理/动画与渲染正确性，选择真实游戏验证；评估独立 GPU 3D 路径。
2. **核心之间的协调**：优化线程和任务调度、同步等待、主线程与工作池交接，降低音频、GC、像素准备和 GPU 提交之间的争用。
3. **负载与帧时间**：测量各任务耗时和队列阻塞，优化负载分配、峰值、缓存与内存退路，优先改善连续动作和复杂场景的稳定性。
4. **兼容与恢复**：继续改善音频、存档恢复、异常边界和设备差异。

路线不承诺固定完成时间；每项改进需要同场景、同版本、真实设备证据，不能只凭主机短测声称所有游戏满帧。
